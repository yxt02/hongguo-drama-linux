# Linux 播放与转码优化计划

以 `v1.74.11-linux`（`da76be0`）为基线。目标是在 Ubuntu 上缩短起播和切集等待，减少播放中断和 CPU 占用，同时保留片源兼容性。分三步实施，分别验证直播放、硬件转码和预取调度。首轮只改 Linux 播放路径，沿用现有播放器、取源和下载逻辑。

## 已确认的现状

- Linux 默认使用 H.264 兼容模式。本机没有保存全局解码模式，实际继承了这个默认值。兼容路径在未命中缓存时要等整集转换完成，连原本已是 H.264 的输入也会进入重编码流程。可在播放器点击「本剧：兼容解码 · 恢复自动」，对当前剧切回自动。
- 自动模式的解码检测和媒体错误可以触发当前集转码。一次回退成功还可能让整部剧记住兼容模式。历史日志能看到转码结果，无法确定用户那次中断由解码检测、媒体错误还是切集等待引起。
- 当前集起播后，程序会按前后各 5 集的缓存窗口预取，后续集优先。兼容模式的后台任务串行下载并转换，前台任务可以加入同一集的在途转换。不同集的前台与后台转码仍可能重叠。
- 本机为 Ubuntu 26.04.1 LTS、Intel Core i5-1135G7 / Iris Xe。用随包 Electron 在独立配置中播放本地 1080p HEVC 样本约 6.5 秒，诊断报告为 `VaapiVideoDecoder`，期间无掉帧。现行兼容转码编码器选择没有 VAAPI 候选，本机日志实际使用 `libx264`。

同一段 12 秒、1080p 30 fps 的本地样本，用随包 FFmpeg 得到以下基线。硬件转码使用 Intel VAAPI 做 HEVC 解码和 H.264 编码。两份转码输出均经 FFprobe 验证为原尺寸、原帧率的 H.264。测试不含取源和下载，未测整机功耗，也未比较两个编码器的画质。

| 处理方式 | 实际耗时 | 累计 CPU 时间 |
| --- | ---: | ---: |
| CPU 只解码 | 0.67 秒 | 2.60 秒 |
| CPU 转码为 H.264 | 6.39 秒 | 43.12 秒 |
| Intel VAAPI 转码为 H.264 | 0.96 秒 | 0.51 秒 |

## 1. 默认直接播放原片

- Linux 在未设置解码模式时默认使用 `auto`。检查设置加载与首集选择的先后顺序，确保首次播放采用读到的设置。保留已有的全局设置和每剧明确选择。旧版每剧兼容记录混合了手动选择和自动学习，无法可靠区分，保留旧记录并继续提供「恢复自动」。
- 在自动模式中，先尝试播放通过现有校验的 H.264 或 HEVC 原片。保留已知 HEVC 不受支持时的提前回退。手动选择兼容模式时，如果输入已经是可直接播放的 H.264，可直接复用。明确要求重新转码，或原片的确解码失败时，再走修复路径。
- 收紧播放中回退条件。区分缓冲、拖动、切源、暂停、暗场和真实解码失败。可用时参考实际呈现的帧或解码帧计数。暗场且帧仍在更新时继续播放。网络故障沿用取源恢复，解码失败才尝试兼容转换。
- 自动回退按当前片源和播放尝试限次，避免一集故障将后续整部剧自动切到兼容模式。继续保留手动选择、原进度续播和暂停状态。诊断日志记录触发原因、编码、集序号、缓存命中和结果，排除账号、片源 URL、请求签名和密钥。

入口：[播放器](../src/components/Player.jsx)、[解码检测](../src/decodeWatch.js)、[默认设置与播放器 IPC](../main.js)。

## 2. 必要的转码优先使用 Intel VAAPI

- 为 Linux 播放专用的兼容转码增加 VAAPI 候选。按当前用户可访问的 DRM 渲染节点探测，优先选择可用的 Intel 核显。设备编号会变，使用稳定设备路径或动态探测，勿把本机的 `renderD129` 写进程序。编码器出现在列表里只说明随包 FFmpeg 编译了该能力，仍要验证设备初始化和实际编码。
- 优先尝试 VAAPI 硬件解码与 H.264 硬件编码。为 VAAPI 使用独立的输入参数和像素格式处理，验证 8 位和 10 位输入。设备不可用、输入不支持、运行失败或输出校验失败时，按有限次数降到已有编码路径和 `libx264`。取消或切集属于正常结束，不触发再次编码。
- 沿用尺寸与清晰度验证、FFprobe 输出检查、临时文件和成功后原子替换。兼容输出本身出现解码错误时，保留用软件重新生成的修复入口。兼容合并也调用现有编码器选择函数，播放专用参数应与合并路径隔离。
- 记录实际采用的编码器、转码耗时和降级原因。验证加速后输出尺寸、声音、拖动和续播正常，再比较编码速度与画质。

入口：[主进程的兼容转码、取消与缓存](../main.js)。FFmpeg 设备与加速参数参见 [FFmpeg 文档](https://ffmpeg.org/ffmpeg.html#Advanced-Video-options)。

## 3. 让后台预取服务于切集

- 保留前后各 5 集作为缓存保留窗口。后台优先准备下一可播集的原片。仅在明确需要兼容时预转码下一集，完成后再考虑紧随其后的可播集。无需转换的片源直接复用。跳过锁定集，沿用本地原件及清晰度校验。
- 同一片源、集和画质只保留一份在途任务。切集时把下一集的后台任务提升为前台，复用已有下载和转换。前台与其他集的后台转换冲突时，优先保障当前集。换剧、跳集、改画质或退出时取消过期任务，并防止旧结果回写当前画面或进度。
- 检查兼容缓存的身份校验。现有身份可包含输入文件路径、大小和修改时间。测试先转换再预取原片、切集和重启后同一有效结果能否复用。只在能证明等价时共用缓存。片源、画质或本地输入实际变化时仍应失效。
- 后台工作不遮挡当前视频。前台需要等待时，分别报告取源、缓冲或转换，便于判断卡在哪一步。

入口：[预取队列与切集](../src/components/Player.jsx)、[播放缓存](../src/native/playback-cache.js)、[任务复用与回收](../main.js)。

## 验收与交付

1. 先用现有测试框架覆盖关键行为。调整固定旧行为的 `check-default-compat.cjs`、`check-series-decode.cjs` 和 `check-next-cache.cjs`。沿用 `check-decode-watch.cjs`、`check-decode-fallback.cjs`、`check-compat-lifecycle.cjs`、`check-playback-cache.cjs` 和 `check-player-resume.cjs`，覆盖暗场、拖动、缓冲、确凿失败、取消、过期结果及进度恢复。
2. 用带真实媒体样本的 `npm run test:playback` 跑完整回归，再执行 `npm run build:react`。构建与启动方式见 [Linux 开发与验证](DEVELOPMENT.md)。需要验证 Linux 打包时，使用临时目录和独立应用配置测试生成的包。
3. 在目标 Ubuntu 上验证 H.264 和 HEVC 的实际首帧、音画、拖动、切集和倍速。至少正常连续播放三集，确认可直接播放的片源不触发转码。再分别验证真实回退、核显可用与不可用、后台任务接管、切集取消、回看缓存以及旧设置继续生效。
4. 用同一片段和同一输出规格重测 CPU 与 VAAPI，记录首帧、切集等待、完整转码耗时和实际编码器。真实联网试播与本地媒体测试分别记录，注明遇到的片源错误和未覆盖的系统或硬件。

实施时使用独立分支或工作树，保留现有安装和观看数据用于对照。交付代码、测试结果和本机试播记录，验证完成后再决定是否替换正式安装。
